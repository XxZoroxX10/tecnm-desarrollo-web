Conceptos desde cero

Cuatro ideas que sostienen toda la sesión

01Excepción

Situación que interrumpe el flujo normal y debe manejarse de forma explícita.

Como un semáforo en rojo: el viaje se detiene y hay que decidir qué hacer.
02Manejador de errores

Función central que transforma una excepción en una respuesta HTTP consistente.

Como la mesa de atención al cliente: recibe el problema y da una respuesta uniforme.
03Sobre de error (envelope)

Estructura JSON común para todos los errores, con código y mensaje.

Como un formato único de queja: siempre tiene folio y descripción.
04404 vs 422

404: el recurso no existe; 422: el recurso existe pero los datos no son válidos.

404: la dirección no existe; 422: la dirección existe pero el paquete está mal armado.
Fundamentos

Manejo Global de Errores y Estandarización de Respuestas

Una API profesional nunca debe colapsar emitiendo un traceback de código o un error HTTP 500 no capturado.

01. Excepciones Semánticas (HTTPException)

Lanzamiento de excepciones estructuradas indicando código de estado y detalle JSON legible.

Interrumpe la ejecución del handler actual y delega la respuesta al middleware de errores.

02. Manejadores Globales de Excepciones

Capturadores centralizados (@app.exception_handler) que transforman excepciones no controladas en JSONs uniformes.

Previene la fuga de información sensible (variables de entorno, rutas de código o passwords) al cliente.

03. Estructura Estándar de Errores JSON

Respuesta uniforme de error: {'status': 'error', 'code': 404, 'detail': '...', 'timestamp': '...'}.

Facilita la captura y despliegue de alertas en las aplicaciones frontend.

Captura de Errores no Manejados

Si ocurre una división por cero o falla de DB, el manejador raíz intercepta el fallo, registra el log interno y emite un HTTP 500 limpio.

Mantiene la estabilidad del proceso del servidor web.

Respuestas de Error en Pydantic

FastAPI captura automáticamente RequestValidationError y lo transforma en un HTTP 422 detallado.

Ahorra código repetitivo de validación manual.
Errores comunes

Antipatrones en Respuestas de Error

Estos son los puntos de falla que la verificación de hoy está diseñada para detectar.

Antipatrones que debes evitar

  • Retornar un traceback de Python o PHP en la respuesta HTTP expuesto al usuario en producción.
  • Retornar HTTP 200 OK con un cuerpo JSON que contiene {'error': 'Usuario no encontrado'}.
  • Uso indiscriminado de errores HTTP 500 para fallos causados por datos inválidos del cliente (que corresponden a 400/422).

Cómo lo comprueba el cuaderno

  • Un libro existente responde 200 HTTP 200
  • Un libro inexistente responde 404 con sobre de error HTTP 404
  • Los datos inválidos responden 422 con sobre de error HTTP 422
  • Un libro válido sigue respondiendo 201 HTTP 201
No se evalúa cómo escribes el código: se evalúa el comportamiento que el cliente observa.
El reto de hoy: resultado final

Tus errores se verán exactamente así

así se verá el resultado
GET /api/libros/99
HTTP/1.1 404 Not Found
{"error":{"codigo":"NO_ENCONTRADO","mensaje":"El libro 99 no existe"}}

POST /api/libros  {"titulo": ""}
HTTP/1.1 422 Unprocessable Entity
{"error":{"codigo":"VALIDACION","mensaje":"Revisa los datos enviados"}}

Nunca:
HTTP/1.1 500 Internal Server Error
{"detail":"Traceback (most recent call last)..."}

Lo que debe cumplirse

  • Define LibroNoEncontrado y regístralo con un handler que responda 404.
  • El cuerpo del 404 es {"error": {"codigo": "NO_ENCONTRADO", "mensaje": ...}}.
  • Los errores de validación responden 422 con el mismo sobre y codigo VALIDACION.
  • La API inicia con el libro 1 (Rayuela) para que el caso feliz exista.
  • GET /api/libros/1 responde 200; GET /api/libros/99 responde 404.
  • Ningún caso debe producir 500.
