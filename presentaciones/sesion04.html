Conceptos desde cero

Cuatro ideas que sostienen toda la sesión

No son definiciones para memorizar: son modelos mentales para decidir mejor frente al código.

01URI

Identificador único de un recurso dentro de la API.

Como la dirección de una casa: no dice qué hacer allí, solo dónde está.
02Parámetro de ruta

Parte de la URI que identifica un recurso concreto, por ejemplo /libros/7.

Como el número de expediente: identifica exactamente un documento.
03Parámetro de consulta

Filtro opcional después de ?, por ejemplo /libros?genero=novela.

Como los filtros de una búsqueda: no cambian el recurso, acotan la lista.
04Colección y recurso

Una colección es /libros; un recurso concreto es /libros/7.

Como el estante completo frente a un libro específico.
Fundamentos

Principios de Diseño de APIs RESTful

REST (Representational State Transfer) organiza la arquitectura web en torno a recursos identificados por URIs jerárquicas y sustantivas.

01. URIs Basadas en Sustantivos Plurales

Las URIs identifican recursos (/api/v1/usuarios), nunca acciones (/api/v1/obtenerUsuarios).

La acción a realizar sobre el recurso la determina exclusivamente el verbo HTTP.

02. Jerarquía y Sub-Recursos

Representación de relaciones entre entidades mediante anidamiento lógico: /api/v1/usuarios/{id}/pedidos.

Mantiene la estructura de rutas intuitiva y predecible.

03. Desacoplamiento Cliente-Servidor

El servidor expone datos y estado; el cliente se encarga de la presentación y la interfaz de usuario.

Permite reutilizar la misma API para clientes Web, Móviles e Integraciones IoT.

Cómo funciona por dentro

Parámetros de Ruta vs Query Parameters

Selección de canales de entrada según la intención de la búsqueda:

Path Parameters (/recursos/{id})

Se utilizan para identificar un recurso específico de forma única en la jerarquía.

Su ausencia en la URI provoca un error de ruteo HTTP 404 Not Found.

Query Parameters (/recursos?limit=10&page=2)

Se utilizan para filtrar, ordenar, paginar o buscar sobre una colección de recursos.

Son opcionales y no alteran la identidad base de la URI.
Errores comunes

Antipatrones en Diseño RESTful

Estos son los puntos de falla que la verificación de hoy está diseñada para detectar.

Antipatrones que debes evitar

  • Incluir verbos dentro de la URI (ej. /api/v1/crear_producto en lugar de POST /api/v1/productos).
  • Anidamiento excesivo de recursos (> 2 niveles de profundidad como /tiendas/1/estantes/2/cajas/3/productos), volviendo la API difícil de mantener.
  • Retornar arreglos JSON crudos en la raíz en lugar de objetos JSON envueltos ({'data': [...]}).

Cómo lo comprueba el cuaderno

  • Libros del autor 1 HTTP 200
  • Filtro por género y límite HTTP 200
  • Un autor inexistente produce 404 HTTP 404
  • La colección completa de libros HTTP 200
No se evalúa cómo escribes el código: se evalúa el comportamiento que el cliente observa.
El reto de hoy: resultado final

Tu jerarquía de recursos responderá así

así se verá el resultado
$ curl "http://127.0.0.1:8000/api/autores/1/libros"
HTTP/1.1 200 OK
{"autor_id":1,"libros":[
  {"id":1,"titulo":"Cien años de soledad","genero":"novela"},
  {"id":2,"titulo":"Doce cuentos peregrinos","genero":"cuento"}
]}

$ curl "http://127.0.0.1:8000/api/autores/1/libros?genero=cuento&limite=1"
HTTP/1.1 200 OK
{"autor_id":1,"libros":[
  {"id":2,"titulo":"Doce cuentos peregrinos","genero":"cuento"}
]}

$ curl "http://127.0.0.1:8000/api/autores/99/libros"
HTTP/1.1 404 Not Found
{"detail":"Autor no encontrado"}

Lo que debe cumplirse

  • GET /api/autores/{autor_id}/libros responde 200 con los libros del autor.
  • El parámetro opcional genero filtra por género y limite recorta la lista.
  • GET /api/autores/99/libros responde 404 si el autor no existe.
  • No incluyas verbos en las rutas: la acción la define el método HTTP.
  • Siembra exactamente: autor 1 Gabriel García Márquez con «Cien años de soledad» (novela) y «Doce cuentos peregrinos» (cuento); autor 2 Julio Cortázar con «Rayuela» (novela).
