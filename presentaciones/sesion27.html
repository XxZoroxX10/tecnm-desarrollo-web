Conceptos desde cero

Cuatro ideas que sostienen toda la sesión

No son definiciones para memorizar: son modelos mentales para decidir mejor frente al código.

01Inyección SQL

Insertar SQL dentro de un dato para alterar la consulta original.

Como colar una instrucción extra en un formulario de pedido.
02Concatenación

Unir texto de la consulta con datos del usuario; es la puerta de entrada del ataque.

Como mezclar la firma de un cheque con el monto escrito por otra persona.
03Consulta parametrizada

Consultar con marcadores y pasar los valores por separado.

Como un formulario con casillas: el dato no cambia la estructura.
04Menor privilegio

La cuenta de la base solo puede hacer lo estrictamente necesario.

Como dar una llave que abre una puerta, no todo el edificio.
Fundamentos

Inyección SQL (OWASP Top 10 A03) y Consultas Parametrizadas

SQL Injection ocurre cuando entradas no confiables se concatenan directamente en cadenas de consulta SQL.

01. Mecánica del Ataque SQLi

Un atacante ingresa ' OR '1'='1 alterando la lógica del parser SQL para saltarse la autenticación o extraer tablas enteras.

Es una de las vulnerabilidades más destructivas en la historia de la web.

02. Consultas Parametrizadas (Prepared Statements)

Separación física entre el código de la consulta y los datos de entrada.

El motor SQL compila la plantilla primero; los datos se tratan estrictamente como valores literales, nunca como código ejecutable.

03. Protección Nativa del ORM

Los ORMs como SQLAlchemy compilan todas las consultas utilizando sentencias preparadas por defecto.

Neutralizan automáticamente los intentos de inyección SQL sin esfuerzo adicional del desarrollador.

Cómo funciona por dentro

Compilación de Sentencias Preparadas

Diferencia entre concatenación frágil y parametrización:

Concatenación Vulnerable (Prohibida)

sql = 'SELECT * FROM users WHERE email = ' + input_usuario.

El texto del usuario altera el árbol sintáctico de la consulta SQL.

Parametrización Segura

sql = 'SELECT * FROM users WHERE email = :email', params={'email': input_usuario}.

El motor trata :email como un contenedor aislado de datos de texto.
Errores comunes

Vulnerabilidades Frecuentes de SQLi

Estos son los puntos de falla que la verificación de hoy está diseñada para detectar.

Antipatrones que debes evitar

  • Uso de SQL crudo con interpolación de cadenas f'SELECT * FROM {tabla}' o text(...) mal utilizado en ORMs.
  • Concatenar nombres de columnas o tablas dinámicamente desde parámetros de la URL.
  • Confiar en filtros de palabras clave manuales (replace('UNION', '')) en lugar de usar sentencias preparadas.

Cómo lo comprueba el cuaderno

  • Una búsqueda normal encuentra un libro HTTP 200
  • El payload de inyección no devuelve toda la tabla HTTP 200
  • El acceso por id sigue funcionando HTTP 200
  • La consulta usa parámetros
No se evalúa cómo escribes el código: se evalúa el comportamiento que el cliente observa.

Lo que debe cumplirse

  • Siembra «Cien años de soledad» (id 1) y «Rayuela» (id 2) como datos de prueba.
  • GET /api/libros/buscar?titulo=... busca por coincidencia.
  • La consulta usa parámetros, nunca concatenación de cadenas.
  • El payload ' OR '1'='1 no devuelve toda la tabla.
  • GET /api/libros/{id} sigue funcionando.
