Conceptos desde cero

Cuatro ideas que sostienen toda la sesión

No son definiciones para memorizar: son modelos mentales para decidir mejor frente al código.

01Dependencia

Objeto o función que un endpoint necesita para trabajar.

Como la batería de un control: el control no la fabrica, solo la usa.
02Inyección de dependencias

Recibir las dependencias desde afuera en lugar de crearlas dentro del endpoint.

Como pedir los ingredientes a la despensa en vez de salir a cosecharlos.
03Depends

Mecanismo de FastAPI que resuelve una dependencia antes de ejecutar el endpoint.

Como el asistente que prepara la mesa antes de que llegue el comensal.
04Inversión de control

El código de alto nivel no decide qué implementación concreta usar.

Como un enchufe estándar: no importa qué aparato conectes, encaja.
Fundamentos

Inversión de Control (IoC) y Gestión de Recursos

La inyección de dependencias permite que los componentes reciban sus colaboradores externos en lugar de instanciarlos directamente.

01. Inversión de Control (IoC)

En lugar de hacer servicio = UsuarioService() dentro del endpoint, el framework inyecta la instancia lista para usar.

Promueve el bajo acoplamiento y la alta cohesión del código.

02. Sistema Depends() en FastAPI

Declara dependencias como parámetros de función evaluados automáticamente en cada request.

Permite componer grafos de dependencias jerárquicos (ej. Auth -> Permisos -> Base de Datos).

03. Ciclo de Vida por Petición (Request-Scoped)

Garantiza que recursos compartidos (como conexiones de DB) se abran al inicio de la petición y se cierren al terminar.

Utiliza generadores (yield) para asegurar limpieza determinista de recursos.

Cómo funciona por dentro

Gestión de Contexto y Limpieza Automática

Patrón Context Manager en dependencias web:

Dependencias con Yield

def get_db(): db = Session(); try: yield db; finally: db.close().

El bloque finally se ejecuta siempre, incluso si el endpoint lanza una excepción HTTP.

Sustitución en Pruebas (Dependency Overrides)

app.dependency_overrides[get_db] = get_test_db.

Permite inyectar bases de datos SQLite en memoria durante las pruebas automatizadas.
Errores comunes

Puntos de Falla en Inyección de Dependencias

Estos son los puntos de falla que la verificación de hoy está diseñada para detectar.

Antipatrones que debes evitar

  • Instanciar conexiones de base de datos como variables globales sin control de pool ni cierre por petición.
  • Dependencias con estado mutable compartido entre hilos (*Race Conditions* en concurrencia).
  • Olvidar el bloque finally provocando fugas de conexiones (*Connection Leaks*) en la base de datos.

Cómo lo comprueba el cuaderno

  • El diagnóstico revela el repositorio inyectado HTTP 200
  • El endpoint inyectado crea un libro HTTP 201
  • El repositorio conserva el estado HTTP 200
  • La validación sigue en el borde HTTP 422
  • El endpoint usa Depends
  • Existe la función de inyección
No se evalúa cómo escribes el código: se evalúa el comportamiento que el cliente observa.
El reto de hoy: resultado final

Tu endpoint recibirá el repositorio inyectado

así se verá el resultado
GET /api/diagnostico
HTTP/1.1 200 OK
{"repositorio":"RepositorioMemoria"}

POST /api/libros
{"titulo":"Rayuela","anio":1963}
HTTP/1.1 201 Created
{"id":1,"titulo":"Rayuela","anio":1963}

GET /api/libros
HTTP/1.1 200 OK
{"libros":[{"id":1,"titulo":"Rayuela","anio":1963}]}

Lo que debe cumplirse

  • Existe una función get_repositorio() que devuelve una instancia de RepositorioMemoria.
  • Los endpoints de libros reciben el repositorio con Depends(get_repositorio).
  • GET /api/diagnostico responde {"repositorio": "RepositorioMemoria"}.
  • El CRUD mantiene el contrato: GET 200, POST 201, datos inválidos 422.
4 casos + 2 comprobaciones en el verificador. Sin pasos intermedios: tú decides la estructura.
El endpoint no crea el repositorio: lo recibe. Esa es la diferencia entre acoplarse y depender de una interfaz.
