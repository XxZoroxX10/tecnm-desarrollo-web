Fundamentos

Optimización de Consultas ORM y Problema N+1

El uso ingenuo de relaciones en ORMs puede desencadenar cientos de consultas repetitivas degradando drásticamente el rendimiento.

01. El Problema del N+1

Ocurre cuando se consulta 1 lista de N elementos y luego el ORM emite N consultas individuales para traer sus hijos.

Convierte una operación de milisegundos en segundos de latencia de red.

02. Carga Ansiosa (selectinload / joinedload)

Estrategias de precarga que traen el objeto y sus relaciones en 1 o 2 consultas SQL optimizadas.

selectinload usa WHERE id IN (...); joinedload realiza un LEFT OUTER JOIN.

03. Filtros, Agregaciones y Paginación

Uso de select(), where(), group_by(), func.count(), limit() y offset().

Sustituye el procesamiento en RAM de Python/PHP por el motor optimizado de SQL.

Diferencia entre Joined vs Selectin

joinedload es ideal para relaciones 1:1 o M:1; selectinload es óptimo para relaciones 1:N y N:M.

Evita la multiplicación cartesiana de filas en arreglos grandes.

Paginación Eficiente (offset / limit)

Obligatoria en colecciones masivas para no cargar cientos de miles de registros en RAM.

Reduce la huella de memoria del proceso del servidor.
Errores comunes

Antipatrones en Consultas ORM

Estos son los puntos de falla que la verificación de hoy está diseñada para detectar.

Antipatrones que debes evitar

  • Iterar sobre una colección de objetos sin usar selectinload, disparando el problema N+1.
  • Cargar colecciones enteras con .all() sin paginar en endpoints públicos.
  • Realizar filtrado de listas en memoria con Python ([x for x in res if x.activo]) en lugar de usar cláusulas where() en SQL.
